# com.cdsoftware.requestprocessor

Plugin for customizing automatic emails generated by the iDempiere Request Processor.

The standard iDempiere processor sends request notification emails using the translated `AD_Message` as subject and `R_Request.Summary` as plain text body. This plugin keeps the standard behavior as fallback, but allows each request event to use an `R_MailText` template, including HTML templates.

## Request Processor Email Templates

### Runtime Replacement

The plugin registers a custom `IServerFactory`:

```text
com.cdsoftware.requestprocessor.component.RequestProcessorFactory
```

The factory returns:

```text
com.cdsoftware.requestprocessor.server.CDSRequestProcessor
```

The OSGi component is declared in:

```text
OSGI-INF/RequestProcessorFactory.xml
```

with:

```text
service.ranking = 100
```

The standard iDempiere request processor factory has ranking `0`, so this plugin factory is selected first by `AdempiereServerMgr`. iDempiere still prevents duplicate processors by `MRequestProcessor` model class.

After installing or updating the plugin, restart iDempiere or reload the Server Manager to ensure the custom processor replaces the standard one.

### Template Configuration Table

Templates are configured in:

```text
CDS_RequestMailTemplate
```

Generated model classes:

```text
com.cdsoftware.requestprocessor.model.I_CDS_RequestMailTemplate
com.cdsoftware.requestprocessor.model.X_CDS_RequestMailTemplate
com.cdsoftware.requestprocessor.model.MRequestMailTemplate
```

Main columns:

```text
CDS_EventCode
R_RequestType_ID
R_MailText_ID
SeqNo
IsActive
AD_Client_ID
AD_Org_ID
```

`R_MailText_ID` points to the mail template to use.

`CDS_EventCode` identifies the request processor event:

```text
RequestDue
RequestAlert
RequestInactive
RequestEscalate
RequestUpdated
```

`R_RequestType_ID` is optional. If it is empty, the record acts as a general fallback template for the event. If both a general row and a request-type-specific row exist, the specific row wins.

Template priority:

```text
1. Same R_RequestType_ID
2. Empty R_RequestType_ID
3. Same AD_Org_ID
4. AD_Org_ID = 0
5. Same AD_Client_ID
6. AD_Client_ID = 0
7. SeqNo
8. CDS_RequestMailTemplate_ID
```

If no active `CDS_RequestMailTemplate` record is found for an event, the plugin uses the native iDempiere behavior.

### Supported Events

`RequestDue`

Used when a request reaches its next action date, and also by the standard processor when a due request transitions into overdue.

Requires the request type option:

```text
EMail When Due = Y
```

or, for the overdue transition path:

```text
EMail When Overdue = Y
```

`RequestAlert`

Used for overdue alert reminders.

Controlled by the Request Processor:

```text
OverdueAlertDays
RemindDays
```

Requires the request type option:

```text
EMail When Overdue = Y
```

`RequestInactive`

Used for inactivity alerts.

Controlled by the Request Processor:

```text
InactivityAlertDays
RemindDays
```

`RequestEscalate`

Used when a request is escalated to a supervisor.

Controlled by the Request Processor:

```text
OverdueAssignDays
Supervisor_ID
```

The plugin preserves the standard recipient behavior: the email is sent to the request responsible user and, when different, to the supervisor.

`RequestUpdated`

Used for request change notifications generated by the standard iDempiere request event handler.

This is the email with a subject like:

```text
Request Updated: 10000000
```

The standard handler builds this message from changed request fields, `DateLastAction`, `DateNextAction`, `Summary`, `Result`, and the request mail tag.

To let the plugin send this email instead of the standard handler, this line must exist in `${ADEMPIERE_HOME}/event.handlers.blacklist`:

```text
org.adempiere.base.event.RequestEventHandler[idempiere/requestSendEMail]
```

The plugin includes `RequestEventBlacklistConfigurer`, an immediate OSGi component that creates or updates the blacklist file automatically when the bundle starts. If the file is updated, restart iDempiere so `EventManager` reloads the blacklist.

If the server filesystem does not allow writing to `${ADEMPIERE_HOME}`, the component logs the required manual entry.

This disables only the standard `REQUEST_SEND_EMAIL` delivery. The standard request model events remain active, so iDempiere still creates request actions, request updates, recipients, and notices.

Without this blacklist entry, both handlers listen to the same event and duplicate emails can be sent.

### Manual Testing Notes

Before running the processor, make sure the request belongs to the same client as the processor and is not processed:

```text
R_Request.Processed = N
```

To trigger `RequestDue`:

```text
R_Request.DueType = Scheduled
R_Request.DateNextAction < today
R_RequestType.EMailWhenDue = Y
```

To trigger the overdue `RequestDue` transition:

```text
R_Request.DueType = Due
R_Request.DateNextAction + R_RequestType.DueDateTolerance < today
R_RequestType.EMailWhenOverdue = Y
DateLastAlert is empty or not today
```

To trigger `RequestAlert`:

```text
RequestProcessor.OverdueAlertDays > 0
R_Request.DateNextAction + OverdueAlertDays < today
R_RequestType.EMailWhenOverdue = Y
DateLastAlert is empty or older than RemindDays
```

To trigger `RequestInactive`:

```text
RequestProcessor.InactivityAlertDays > 0
R_Request.Updated + InactivityAlertDays < today
DateLastAlert is empty or older than RemindDays
```

To trigger `RequestEscalate`:

```text
RequestProcessor.OverdueAssignDays > 0
R_Request.IsEscalated = N
R_Request.DateNextAction + OverdueAssignDays < today
```

After escalation, iDempiere sets `IsEscalated = Y`, updates the due type, stores the escalation subject in `Result`, and saves the request. To retest escalation with the same request, reset `IsEscalated` to `N` and adjust the alert dates as needed.

To trigger `RequestUpdated`, change and save a request field monitored by the standard request event handler, for example:

```text
SalesRep_ID
R_Status_ID
PriorityUser
IsEscalated
DateNextAction
```

The recipient list comes from `RV_RequestUpdates_Only` plus the current request responsible user.

### Mail Template Variables

Templates use standard `R_MailText` variables, for example:

```text
@DocumentNo@
@Summary@
@R_Status_ID@
@SalesRep_ID@
@DateNextAction@
```

The plugin sets the request as the parsed PO, so request columns can be used directly in the template.

For each recipient, the plugin also sets the recipient user before parsing, so user variables can be resolved by `MMailText`.

For `RequestUpdated`, these additional variables are available:

```text
@OriginalSubject@
@RequestUpdateMessage@
@RequestUpdateMessageHtml@
@RecipientName@
@SenderName@
```

`@RequestUpdateMessage@` contains the native plain text message generated by iDempiere.

`@RequestUpdateMessageHtml@` contains the native message converted to HTML. The standard header and trailer are escaped as plain text, while the `Summary` block is rendered as an HTML fragment.

### HTML Summary Rendering

The plugin includes:

```text
com.cdsoftware.requestprocessor.model.CDSMailText
```

This class extends `MMailText` and customizes `@Summary@` when the selected `R_MailText` is marked as HTML.

If:

```text
R_MailText.IsHtml = Y
```

and the template contains:

```html
@Summary@
```

then `R_Request.Summary` is interpreted as an HTML fragment. HTML entities such as:

```html
&lt;p&gt;Texto &lt;b&gt;importante&lt;/b&gt;&lt;/p&gt;
```

are decoded and rendered as HTML inside the email body.

If the template is not HTML, `@Summary@` keeps the standard parsing behavior.

### Fallback Behavior

If any of these conditions occurs, the plugin sends the native iDempiere email:

```text
No CDS_RequestMailTemplate row for the event
The row is inactive
R_MailText_ID is empty
The R_MailText record does not exist
```

Native behavior:

```text
Subject = translated AD_Message
Body = R_Request.Summary
Attachment = request.createPDF()
Recipient = SalesRep_ID
```

For `RequestEscalate`, native behavior also includes the supervisor email when applicable.

For `RequestUpdated`, native behavior is preserved by `RequestUpdateMailTemplateEvent` when no `CDS_RequestMailTemplate` row exists for the event.

### Example Configuration

General template for all request types:

```text
CDS_EventCode = RequestAlert
R_RequestType_ID = empty
R_MailText_ID = Alert template
AD_Client_ID = client
AD_Org_ID = 0
SeqNo = 10
IsActive = Y
```

Specific template for one request type:

```text
CDS_EventCode = RequestAlert
R_RequestType_ID = Support Request
R_MailText_ID = Support alert template
AD_Client_ID = client
AD_Org_ID = 0
SeqNo = 10
IsActive = Y
```

The specific template is selected before the general one.

## How it works

### Components

- New callout
  - Create callout in package `com.cdsoftware.requestprocessor.callout`, extends from `CustomCallout`
  - Annotate it with the `@Callout` annotation at class level

- New process
  - Create process in package `com.cdsoftware.requestprocessor.process`, extends from `CustomProcess`
  - Annotate it with the `@Process` annotation at class level

- New form
  - Create form in package `com.cdsoftware.requestprocessor.form`, extends from `CustomForm`
  - Annotate it with the `@Form` annotation at class level

- New event
  - Create event in package `com.cdsoftware.requestprocessor.event`, extends from `CustomEvent`
  - Annotate it with the `@EventTopicDelegate` annotation at class level

- New model (extends form class X)
  - Create model in package `com.cdsoftware.requestprocessor.model`, extends class `X`. Example: `X_TL_TableExample -> MTableExample`
  - Annotate it with the `@Model` annotation at class level
  - More information
    - <https://wiki.idempiere.org/en/Developing_Plug-Ins_-_IModelFactory>
    - <https://wiki.idempiere.org/en/Developing_iDempiere_4:_Create_a_new_class_model_with_window_and_tabs#Model_generator>

### Utils

- `FileTemplateBuilder`: Creates complex text file using [freemarker](https://freemarker.apache.org/), example:

```java
FileTemplateBuilder.builder()
    .file("invoice-template.xml")
    .inject("invoice", new Invoice())
    .export("invoice.xml")
```

The `invoice-template.xml` file:

```xml
<invoice>
    <name>${invoice.name}</name>
    <id>${invoice.id}</id>
    <lines>
        <#list invoice.invoiceLines as line>
        <line>
            <product name="${line.product}" price="${line.price}"/>
        </line>
        </#list>
    </lines>
</invoice>
```

- `KeyValueLogger`: Use CLogger to log information with a key/value format, example:

```java
KeyValueLogger keyValueLogger = KeyValueLogger.instance(App.class);
keyValueLogger.message("Hello World!!").info();
```

The output:

```bash
20:34:24.270 ELogLoginInfo.log: message="Hello World!!"
```

Other output examples:

```css
19:50:16.044 OpenTransactionInterceptor.log: dateTime="2020-02-12 19:50:16.039 -0500" httpMethod="POST" client="11" language="es_CO" endpoint="/api/auth/login" transaction="Trx_e1dcd314-a508-44c1-9a0c-d34d4caacb2b" [33]
19:50:16.157 CloseTransactionInterceptor.log: dateTime="2020-02-12 19:50:16.156 -0500" httpStatus="200" endpoint="/api/auth/login" transaction="Trx_e1dcd314-a508-44c1-9a0c-d34d4caacb2b" [33]
```

- `SqlBuilder`: It is a wrapper for StringBuilder, allows you to create sql from files, example:

```java
String sql = SqlBuilder.builder().file("read-bpartner.sql").build()
```

The `read-bpartner.sql` file:

```sql
-- This query reads the partners using as filter "is vendor"

from c_bpartner
where isvendor = ?
```

- `TimestampUtil`: to create timestamp objects, example:

```java
Timestamp currentTime = TimestampUtil.now();
```

### Adding a new library

Add the new dependency (`artifacItem`) to the [pom.xml](pom.xml) file in the `artifactItems` attribute, example:

```xml
    <artifactItems>
        <artifactItem>
            <groupId>com.google.guava</groupId>
            <artifactId>guava</artifactId>
            <version>28.0-jre</version>
        </artifactItem>
    </artifactItems>
```

Then, add a new classpath entry in the [.classpath](.classpath) file, example:

```xml
    <classpathentry kind="lib" path="lib/guava.jar"/>
```

Verify you are including the folder `lib` in the [build.properties](build.properties) file, exaple:

```properties
bin.includes = .,\
               META-INF/,\
               OSGI-INF/,\
               lib/
```

Finally, add the new dependency in de [MANIFEST.MF](META-INF/MANIFEST.MF) file as a `Bundle-ClassPath` attribute, example:

```manifest
Bundle-ClassPath: .,
 lib/guava.jar
```
